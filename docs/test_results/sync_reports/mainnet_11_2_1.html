Mainnet Sync Report - 11.2.1

Mainnet sync from genesis, comparing cardano-node 11.2.0 with the 11.2.1 release. The main purpose of 11.2.1 is to address the performance regressions identified in the unreleased 11.2.0 build. This report evaluates the release’s sync time, memory consumption, and CPU utilization against that build.

An intermediate experimental run verified the fixes before their inclusion in 11.2.1; see the fix-verification report. It provides supporting evidence, not the primary baseline for this release report.

Most effective startup settings match between 11.2.0 and 11.2.1, but the maximum snapshot delay changes from six hours to one hour. The kernel and CLI versions also change, so this is not a fully controlled comparison.

Summary

  • Memory consumption drops substantially. Peak RSS falls from 22.08 to 16.98 GiB (-23.1%), and peak garbage-collector live data falls from 18.03 to 11.00 GiB (-39.0%). The reduction remains over matching chain ranges.

  • Sync completes about five hours sooner. Reported sync time falls from 132,111 to 113,689 seconds (-13.9%), despite reaching 1,090,011 more slots. Babbage takes 21.6% less time over the same chain range and accounts for 72.4% of the whole-run saving.

  • CPU utilization improves without more aggregate CPU work. Mean CPU load rises from 112% to 118% of one core, while total CPU time falls 9.6%.

  • Snapshot scheduling changes substantially. Completed writes increase from nine to 179, and major collections increase 59.5%. Total allocation falls 2.4%. The changed maximum snapshot delay limits causal attribution.

  • The improvements are not uniform. Early-chain memory remains higher, and delays persist around Babbage epochs 461-475. Whole-run peak RSS is still 10.0% above the historical 11.0.1 baseline, which used different software and configuration.

Sync Performance

11.2.1 finishes 18,422 seconds (5 h 7 min) sooner than 11.2.0 while reaching 1,090,011 more slots (+0.54%). Babbage saves 13,334 seconds over the same 61.344 million-slot range, accounting for 72.4% of that whole-run saving.

Alonzo saves a further 1,535 seconds (-7.3%). Conway completes 3,645 seconds sooner (-9.1%) while covering more chain. Improvements in these later eras outweigh the smaller differences in early-era timings.

Byron timing boundaries differ from the original 11.2.0 result. That result first observes epoch 4 and counts 4,406,400 Byron slots. The 11.2.1 result records the launch boundary and counts all 4,492,800 slots from epoch 0. Both nodes actually sync from genesis. The apparent Byron slowdown mixes different timing and counting boundaries.

Conway’s recorded length increases from 68.256 million slots in 11.2.0 to 69.552 million in 11.2.1. Recorded throughput rises from 1,707 to 1,913 slots/s (+12.1%). These era lengths use the recorded epoch boundaries, not the exact completion-slot differences.

The Babbage improvement is not uniform. Epochs 400-460 take 19,329 seconds instead of 31,130 (-37.9%), but epochs 461-475 take 9,860 seconds instead of 9,270 (+6.4%). The broader slowdown is reduced, not every local delay.

Memory Consumption

Peak RSS falls by 5.11 GiB and mean RSS by 3.39 GiB. The release uses more memory over some early-chain ranges, but the curves separate in its favor around slots 55-60 million. RSS stays near 15.95 GiB over much of the late chain, then rises to 16.98 GiB around slot 200.25 million. It never exceeds 20 GiB, unlike 11.2.0.

Peak live data falls by 7.03 GiB (-39.0%), and mean live data falls 18.9%. The improvement therefore includes less retained live data, not just reduced unused heap capacity. Major collections increase 59.5%, while total allocation falls 2.4%.

The absence of heap decreases does not itself establish a leak: the release retains a substantially smaller heap while major collections continue. The late increase means this run should not be presented as proof of a permanent post-sync plateau or of behavior over longer periods at the chain tip.

Restricting 11.2.1 to 11.2.0’s exact completion slot includes its late increase, leaving its 16.98 GiB peak unchanged. The memory reduction is therefore not an artifact of comparing different chain endpoints.

The effective maximum snapshot delay does not: it is 3,600 seconds in 11.2.1 versus 21,600 seconds in 11.2.0. The node’s snapshot-policy startup message also confirms the release’s one-hour maximum.

The first snapshot completes more than five hours after the first chain extension in 11.2.0, but after about one minute in 11.2.1. Subsequent release writes complete approximately every 10 minutes. This substantial scheduling change accompanies lower retained data and more major collections, but the comparison does not isolate the contribution of each implementation or configuration change.

This is one run per build, not a repeated benchmark. Peer availability, storage conditions, and other runtime effects are not controlled. The results show substantial improvements in the release relative to 11.2.0, not proof that every historical regression or local delay is resolved.

Supporting Evidence From Fix Verification

Before the release, an experimental build at revision 45aa403634fe2bb8817e65e7edf6b1d639a3bada verified the fixes using the same effective startup settings as 11.2.0, including the six-hour maximum snapshot delay. The verification report calls that build 11.2.0-fix; it was a validation run, not a separate release baseline.

That run supports the release findings in two ways:

  • Peak RSS was 16.75 GiB and peak live data was 10.93 GiB, close to the release’s 16.98 and 11.00 GiB. The lower memory footprint was therefore already observed with the fixes before the release’s snapshot-setting change.

  • It recorded 176 completed snapshot writes, close to the release’s 179, despite retaining 11.2.0’s maximum-delay setting. The change from sparse to frequent writes cannot be explained solely by the release’s shorter maximum.

The verification run completed in 110,485 seconds. The release takes 2.9% longer while reaching 577,201 more slots. Its fixed-length Babbage era takes 9.8% longer, with a deeper utilization trough around epochs 461-475, partly offset by faster syncing elsewhere. This variation limits claims of identical timing across the two fixed builds, but does not change the release’s 13.9% improvement over 11.2.0. Repeated, matched-setting runs would be needed to attribute that variation.

Methodology

RSS, RTS heap, and CPU statistics come from the result JSON files. Memory statistics exclude zero-valued fields, which represent missing resource samples, and require a recorded tip to match the graph script. This yields 130,567 and 112,107 usable memory samples for 11.2.0 and 11.2.1, respectively.

Whole-run means and threshold fractions are sample-weighted, not normalized to equal time spent at each slot. Different sync speeds can change those statistics. Matching-slot checks compare peaks without that weighting issue. Slot bands include their lower bound and exclude their upper bound.

CPU means retain genuine zero-load samples and use stored values without rescaling. The smoothed figure averages samples into one million-slot bands, keeping bands with at least 20 samples. Total CPU time is the change in the node log’s cumulative CPU-tick counter divided by 100.

GC live bytes, major collections, allocation, and completed snapshot writes come from the full node logs. They contain 130,576 and 112,114 resource samples, including samples without a recorded tip. Live-data means are arithmetic means of those samples. Major-GC and allocation totals are the last counter minus the first counter in each resource-log window, not process-lifetime maxima. Allocation uses decimal TB. Snapshot counts include only completed ‘Took ledger snapshot’ events, not the preceding ‘Taking’ events.

Heap decreases count successive decreases among nonzero, tip-associated heap samples in timestamp order. Threshold fractions refer to heap, not RSS. The timing-boundary cross-check uses the first logged chain extension at slot 0 and the recorded sync-completion timestamp. Per-epoch timings use observed epochs: the series begin at epoch 4 for 11.2.0 and epoch 3 for 11.2.1, even though the release’s era summary counts Byron from epoch 0. The final observed epoch is partial and should not be compared as a full epoch.

Graphs use sync_tests/scripts/sync_static_graphs.py with the two result files in table order, explicit labels 11.2.0 and 11.2.1, node mode, and 150 dpi PNG output. The era graph’s legend is placed outside the bars to keep its totals visible.

The supplementary verification measurements use the same calculation methods. Its JSON contains 108,891 usable memory samples, and its full log contains 108,897 resource samples. The verification run took place on November 3-4, 2026.
